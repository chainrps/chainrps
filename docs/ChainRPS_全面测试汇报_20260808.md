## 三、发现的 BUG 与设计缺陷（按严重等级排序）

### 🔴 严重等级：CRITICAL (必须立即修复)

#### BUG-001：揭晓后游戏永久卡在 `reveal` 状态，无兜底结算

**位置**：`rps_backend/service/game_service.py` `reveal_choice()` + `_settleGame` 缺失

**现象**：  
```
双方reveal完成后 → state=reveal, winner=None, is_draw=False → 永久不变
```

**根因**：  
架构约定「后端无博弈权限，胜负判定 100% 依赖链上 GameSettled/DrawHandled 事件同步」（见代码注释 L6-L8）。但：
1. 合约事件监听服务 `contract_service` 在以下场景会失败：RPC不可用、合约地址未配置、WebSocket断连、本地链未启动
2. 失败时后端 **完全没有 fallback 兜底逻辑**
3. 即便是内存降级模式用于前端演示，用户体验也是「出拳后永远看不到胜负」

**影响**：
- 所有玩家对局永久卡在 reveal，无结算
- 玩家统计 (win/loss/draw) 永不更新
- 历史记录显示「进行中」而非胜负
- 商业上无法抽水（fee永远为0）

**修复建议（方案二选一，需决策确认）**：

> 🔵 **【决策项 D-01】后端结算兜底策略选择**

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **A. 本地兜底 + 链事件覆盖** | 双方reveal后后端立即本地结算写库→发WS→写玩家统计；链事件到达后**二次校验**，若不一致以链为准修正（概率<0.01%） | 用户体验100%闭环；99.99%场景无需修正；降级环境也可用 | 修正逻辑复杂（需回滚玩家统计+发修正通知） |
| **B. 仅降级环境启用兜底** | 检测到 contract_service 未初始化/链不可达时才启用本地结算；正式环境严格遵守「链唯一权威」 | 正式环境零信任风险 | 正式环境若RPC挂仍会永久卡 |
| **C. 维持现状** | 什么都不改，依赖运维确保 RPC+监听器99.999%可用 | 实现最简单 | 用户体验差；运维压力大；演示环境不可用 |

#### BUG-002：玩家统计 winner_prize 计算错误

**位置**：`rps_backend/service/game_service.py#L348`

```python
# 当前代码（错误）：
winner_prize = bet_amount - fee if bet_amount > fee else 0

# 正确逻辑（按合约实现）：
# total_prize = bet_amount * 2   (双方下注合计)
# fee = total_prize * feeRate / 10000
# winner_prize = total_prize - fee = bet_amount*2 - fee
```

**影响**：玩家统计中 `total_won` 字段少记了约一倍的奖金（扣除下注本金前 vs 后混淆），统计面板数据错误，排行榜失真。

### 🟠 严重等级：HIGH (上线前修复)

#### BUG-003：出拳协议前后端/接口间不一致

**位置**：`rps_backend/models/__init__.py#L15-L19, L84-L92, L112-L120`

| 接口/模块 | choice 类型 | 合法取值 |
|-----------|-------------|---------|
| 合约 Solidity | `uint8` | 1=石头, 2=布, 3=剪刀 |
| 前端 `Contract.signReveal` | JS Number | 1/2/3 (注释写死) |
| 方案A `RevealChoiceSigRequest.choice` | `int` | 1/2/3 (✅一致) |
| 普通接口 `RevealChoiceRequest.choice` | `Choice(str, Enum)` | **"rock"/"paper"/"scissors"** (❌不一致) |
| 后端 `_verify_commit` 参数 | `int or str` | 两种都兼容 (✅) |

**影响**：
- 前端若走普通 `/api/game/reveal` 直接传 1/2/3 → **422 校验失败**
- 目前前端reveal走合约直连，不常触发此接口；但第三方客户端/测试脚本会踩坑
- 与合约 uint8 语义不一致，增加心智负担

**修复建议**：

> 🔵 **【决策项 D-02】出拳协议统一策略**

- **推荐方案**：统一为 `uint8` 整数 (1/2/3)，与合约一致
- `Choice` 枚举改为 `int` Enum 或同时接受 str/int 两种输入（使用 Pydantic `BeforeValidator`）
- 数据库 `choice1/choice2 TEXT` 列建议改为 `INTEGER` 与合约对齐（当前是 TEXT 存字符串）

---

#### BUG-004：GameState.DRAW 状态语义混淆（从未实际使用）

**位置**：`rps_backend/models/__init__.py#L22-L30` vs 合约 ChainRPS.sol L70-L77

```python
# 当前 GameState 有 DRAW = "draw"
class GameState(str, Enum):
    WAITING = "waiting"
    COMMIT_PHASE = "commit"
    REVEAL_PHASE = "reveal"
    FINISHED = "finished"
    CANCELLED = "cancelled"
    DRAW = "draw"   # ← 问题：从未被写入
```

**合约实际语义**：平局时 `game.status=Finished` 且 `game.isDraw=true`，没有独立的 Draw 状态。  
**现状**：`test_game_flow.py` 第226行断言 `state == "draw"`，永远失败。实际平局后状态仍停留在 `reveal`（BUG-001叠加）。

**修复建议**：删除 `GameState.DRAW` 或改为仅前端展示用逻辑状态，DB/后端统一用 `FINISHED + is_draw=True`。

### 🟡 严重等级：MEDIUM (上线后迭代优化)

#### BUG-005：数据库 choice 列类型与合约不一致

**位置**：`rps_backend/repository/database.py#L101-L102`

```sql
choice1 TEXT, choice2 TEXT, salt1 TEXT, salt2 TEXT
```

合约 choice 是 uint8。TEXT 存 "rock"/"paper"/"scissors" 字符串会导致：
- 无法直接做数值比较（SQL 层判胜负困难）
- 与链上 1/2/3 同步时需要双向映射

#### BUG-006：未准备超时计时器在特定竞态下可能不取消

**位置**：`rps_backend/service/room_service.py#L227-L239` `toggle_ready()`

`_stop_unready_timer` 是按 address 作为 key 查的，同一个 address 不会有两个定时器，逻辑安全。但：
- 玩家A在房间1未准备时 → 被踢→房间重置→加入房间2→重新启动定时器，**60秒计时不是从加入房间2开始算**，旧的 timer 可能提前误触发踢出（因为旧timer存的旧 room_id）
- 可通过在 timer 函数里增加「generation/version 计数器」修复（非紧急）

## 四、性能测试分析

### 4.1 基准测试结果

| 指标 | 实测值 | 评价 | 行业基准参考 |
|------|--------|------|-------------|
| 房间创建吞吐（10并发） | **443 req/s** | 🟢 优秀 | 匹配类游戏 ≥100 req/s 达标 |
| 健康检查 RPS（单线程） | **624 req/s** | 🟢 优秀 | HTTP框架基准 ≥500 良好 |
| API 平均响应时间 | **<20ms** | 🟢 优秀 | WebSocket类游戏 <100ms 无感 |
| 15秒倒计时准时性 | **+2s偏差** | 🟡 可接受 | asyncio.sleep 协程调度级偏差正常 |

### 4.2 性能瓶颈预测

当前内存降级模式性能极高。引入真实 Redis + SQLite WAL 模式后预计：
- 房间创建吞吐下降 30~50% → 仍约 220 req/s → 单实例支撑 **1万 DAU** 无压力
- 瓶颈将出现在：
  1. **链上 RPC 调用**（Polygon 1-2s/tx，需前端做乐观UI）
  2. **合约事件监听轮询间隔**（若用轮询而非 WebSocket）
  3. Bot 并发代提交时的 nonce 管理

### 4.3 性能优化建议（非紧急，二期做）

1. **数据库**：SQLite 切换 WAL 模式 + 增加缓存层（已做Redis），单表 `games` 百万级记录无压力
2. **WebSocket 广播风暴**：`_broadcast_room_list_changed` 当前是全连接广播，用户 >1000 时建议改为「只推送给订阅大厅的客户端」
3. **玩家统计**：`update_player_stats` 每次全量 UPDATE，高并发场景改为「异步队列累计 + 定时刷盘」

### 5.2 链上公平性完整性（核心价值）

✅ **密码学公平性**：  
- 合约使用 `keccak256(abi.encodePacked(uint8 choice, bytes32 salt, address player))`，后端 `_verify_commit` 验证一致
- 后端 `reveal_choice` 不做 salt 校验，完全以链为准（零信任后端 ✅）
- EIP-712 签名动态 chainId 绑定，防跨链重放 ✅
- Relayer 白名单 + deadline + nonce 三重防重放 ✅

❌ **一点风险**：方案B `authorizeRelayer` 授权 7 天期间，relayer 地址若被攻破可代玩家出拳（但无法盗取资金，因为出拳仍需 commit 匹配）。**建议前端加醒目安全提示 + 授权到期自动续约选项**。
