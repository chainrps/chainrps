# ChainRPS 系统架构设计文档（最终定稿）

---

## 一、架构总体核心定位

本项目采用 **「链上强信任确权 + 链下弱辅助体验」混合架构**，彻底解决传统链游中心化作弊风险、纯链游体验卡顿问题。

### 核心铁律（项目架构底线）
- 所有影响**资金、胜负、公平性**的核心逻辑 **100% 链上固化、开源可审计**；
- 所有中心化后端仅承担体验优化，**无任何权限篡改对局、资金、结果**。

系统原生支持 **双运行模式自由切换**，用户可自主选择「便捷中心化匹配」或「极致去中心化零信任模式」，兼顾大众体验与加密原生信任背书。

## 二、双层运行模式（最终确认产品架构）

前端内置两套完全隔离的对局链路，一键切换、数据互不互通，满足不同用户信任需求。

### 模式 A：公共快速匹配模式（默认·大众体验版）

**适用场景**：陌生人随机对战、高频休闲对局、平台核心流量场景

**数据流链路**：用户前端网页 ↔ 云端 FastAPI 后端（匹配/消息） ↔ Polygon 链上合约

**运行逻辑**：
1. 用户选择下注金额，进入后端 Redis 匹配队列；
2. 后端撮合引擎自动匹配同金额在线玩家，完成双人配对；
3. WebSocket 实时推送匹配成功、对方提交、对局状态等消息；
4. 后续**提交哈希、揭晓出拳、胜负判定、资金锁定、手续费结算**全部由用户钱包签名、链上合约自动执行；
5. 后端仅做状态同步展示，不参与任何博弈与资金逻辑。

**信任边界说明**：
- 后端宕机、故障、被攻击不会篡改任何对局结果与用户资产；
- 后端无用户私钥、无交易签名权限、无资金操控权限；
- 仅影响「匹配速度、消息实时性」，不影响公平与安全。

### 模式 B：私密纯净无后端模式（极致去中心化·信任版）

**适用场景**：好友切磋、隐私对局、极致去中心化用户、规避所有中心化服务器信任疑虑

**核心特性**：前端彻底断开所有后端 API / WebSocket 连接，用户零数据上传平台服务器

**标准线上形态（主推，MVP 采用）**：
- 用户访问域名，从静态网页服务器/CDN/IPFS 拉取 HTML/JS/CSS；
- 页面加载完成后，进入模式 B 时：不再发起任何业务 API、WebSocket 请求到 FastAPI 后端；
- **重点区分**：
  - ✅ 首次加载页面资源（HTML、JS 静态文件）≠ 对局业务数据上报后端
  - ✅ 模式 B 阻断的是【游戏业务通信】，不阻断初始静态资源加载
- 页面加载完毕之后，后续所有对局交互，只有：浏览器 ↔ 钱包 ↔ Polygon RPC

**进阶离线形态（可选、非必需，二期附加）**：
- 用户可以把整套前端静态代码下载到本机，本地打开 index.html 直接运行；
- 完全脱离域名、静态服务器，100% 离线文件运行，同样可以进入模式 B；
- **优势**：极致去中心化，网页托管服务商也无法审查；
- **短板**：普通用户操作门槛高，不懂下载源码、本地打开；还会存在部分浏览器跨域安全限制。

**完整数据流精确定义**：
1. 用户访问统一前端站点加载静态资源（HTML/CSS/JS）；
2. 切换至纯净模式后，前端 JS 主动拦截、禁用所有指向业务后端（FastAPI）的接口与 WebSocket 连接；
3. 对局生命周期内不再产生任何游戏业务数据发往运营方服务器；
4. 博弈全流程仅发生：浏览器前端逻辑 ↔ Web3 钱包 ↔ Polygon 智能合约；
5. 该模式不提供自动撮合排队，依靠 matchId（即合约 gameId）通过外部社交渠道邀约好友对战。

**模式 B matchId 说明**：
- matchId 就是链上合约的 gameId；
- 创建者直接调用合约 `createMatch()` 得到 gameId 后分享给好友；
- 好友通过输入 gameId 加入对局。

**信任优势**：
- 完全消除中心化服务器监听、干预、收集数据的可能性；
- 百分百纯链上交互，逻辑公开透明，符合去中心化核心叙事；
- 后端服务下线、故障完全不影响该模式正常使用。

### 模式 B 关键答疑

| 问题 | 解答 |
|------|------|
| 能不能做到「下载 HTML 到本地，断网也能玩？」 | 不能完全断网。JS 代码在本地运行、本地完成 Commit-Reveal 哈希加密 ✅；但必须联网访问 Polygon RPC 节点，读写智能合约 ❌。完全断网无法和区块链交互，不能创建/加入对局、无法提交哈希与开奖。 |
| 会不会出现歧义：用户误以为「本地 HTML = 完全不上网」 | UI 文案必须明确标注，样板文案：【私密纯净对局】✅ 不向 ChainRPS 官方后端传输任何对局信息 ⚠️ 仍需要网络连接 Polygon 区块链节点执行链上交易 |
| 那两种运行路径如何定位？ | 日常普通用户：浏览器访问网页域名（CDN 托管）→ 切换模式 B（主流方案）；加密极客用户：Release 下载前端源码压缩包，本地打开 index.html 运行模式 B（备选增值方案） |

**架构层面重要约束**：
- 前端代码内部的「后端服务域名地址」写在配置常量里；
- 切换模式 B 时，代码直接放弃使用该地址，所有匹配相关接口全部禁用，不存在隐性后台请求；
- 配套保障：前端完整开源，任何人可审计网络请求逻辑，确认模式 B 下无隐秘上报。

## 三、核心公平保密机制架构（防作弊核心）

整套出拳保密体系 **完全在用户前端本地完成**，服务器与第三方均无法窃取、预判。

### 1. 本地 Commit-Reveal 密码学机制（核心保密）

```
用户选择出拳 → 本地生成随机盐值 → 计算哈希密文 → 仅密文上链
                    ↓
              双方提交密文后
                    ↓
        前端公开原始出拳 + 盐值 → 合约校验哈希一致性
```

**详细流程**：
1. 用户前端本地选择：石头 / 剪刀 / 布；
2. 前端本地生成高熵随机盐值 Salt（永不上传、永不对外暴露）；
3. 本地计算哈希密文 `keccak256(choice + salt + address)`（包含玩家地址，防止跨对局重放攻击）；
4. 仅哈希密文上链存储，原始出拳、Salt 全程只存在用户浏览器本地；
5. 双方全部提交密文后，合约自动切换为「揭晓阶段」；
6. 用户手动公开原始出拳 + Salt，合约重新校验哈希一致性；
7. 校验一致生效，不一致直接判定作弊、对局失效。

### 2. 链上强制结算机制（绝对公平）

所有核心规则硬编码在智能合约，开源可审计、不可篡改：

| 规则类别 | 具体内容 |
|----------|----------|
| 资金规则 | 资金锁定、释放规则 |
| 阶段规则 | 对局阶段流转规则（提交期/揭晓期/结束期） |
| 超时规则 | 提交超时 66s、揭晓超时 88s，超时方自动弃权判负 |
| 胜负规则 | 标准石头剪刀布胜负算法 |
| 手续费规则 | 胜者奖金中扣除手续费，费率可由 Owner 调整 |
| 平局规则 | 默认原路退回，平局手续费为非平局的 50% |

### 3. 超时判负机制

| 场景 | 处理方式 |
|------|----------|
| 提交阶段超时 | 未超时方获胜，拿回全部下注（超时方下注全给对方） |
| 揭晓阶段超时 | 未超时方获胜，拿回全部下注（超时方下注全给对方） |
| 超时方出拳方式 | 用户可设置：默认随机出拳，或设置固定出拳值 |
| 触发方式 | 由未超时方主动调用 `claimTimeout()` 触发；后端自动超时判负为兜底功能，非必需 |

### 4. 平局处理机制

| 项目 | 说明 |
|------|------|
| 触发条件 | 双方出拳相同 |
| 资金处理 | 默认原路退回（双方各自拿回自己的下注） |
| 手续费 | 收取非平局手续费的 50%，从双方下注中各扣一半，或从资金池扣除 |
| 触发方式 | 由玩家调用 `handleDraw()` 触发 |
| 用户设置 | 前端可配置平局处理方式（默认原路退回） |

## 四、三层技术架构分层（标准落地结构）

### 1. 客户端层（用户侧 · 完全开源）

**技术**：HTML/CSS/JS + Ethers.js + WalletConnect + FWUI 组件库

**能力**：
- 钱包连接、链上余额读取、交易签名；
- 本地密码学加密（核心保密逻辑）；
- 双模式切换、网络请求隔离；
- 链上数据解析、对局结果可视化展示；
- 支持 USDC/USDT 稳定币显示；
- **全静态运行支持**：前端代码不依赖任何服务端渲染，可独立部署于 CDN/IPFS，支持用户本地下载运行；
- 亮色/暗色双主题支持；
- 列表视图/卡片视图切换支持；
- 统一 UI 组件库（FWUI）管理弹窗、提示等交互组件。

**开源要求**：100% 开源，供社区审计无后门、无静默数据上传。

### 2. 链下服务层（开发者云端 · 体验辅助）

**技术**：Python FastAPI + Redis + WebSocket + SQLite

**能力（仅体验层，无信任权限）**：
- 玩家金额队列撮合、陌生人匹配；
- 实时 WebSocket 对局状态推送；
- 对局日志缓存、历史记录查询（优先后端，性能快；降级链上查询）；
- 链上事件监听、前端状态同步；
- 对局生命周期管理（创建、加入、进行中、结束）。

**信任边界**：无私钥、无交易权限、无资金操控、无结果篡改权限。

**开源策略**：基础通信逻辑开源，风控防刷核心逻辑闭源，兼顾信任与安全壁垒。

**项目结构**：
```
chainrps/
├── contracts/          # 智能合约（链上逻辑）
├── rps_core/           # 后端服务（链下逻辑）
│   ├── api/            # API 层
│   │   ├── routes.py       # 路由定义
│   │   └── endpoints/      # 业务端点（game.py, user.py）
│   ├── service/        # 业务逻辑层
│   │   ├── game_service.py     # 游戏核心逻辑
│   │   ├── matching_service.py # 匹配服务
│   │   └── contract_service.py # 合约交互
│   ├── repository/     # 数据访问层
│   ├── models/         # Pydantic 数据模型
│   ├── config/         # 配置管理
│   ├── utils/          # 工具函数
│   ├── websocket/      # WebSocket 模块
│   └── main.py         # 服务入口
├── web/                # 前端页面（纯静态 HTML/CSS/JS）
│   ├── static/
│   │   ├── css/        # 样式文件
│   │   ├── js/         # JavaScript 文件
│   │   └── html/       # HTML 页面
│   ├── FWUI/           # 独立 UI 组件库
│   └── routers/        # （如有需要）
└── docs/               # 文档
```

**结构设计说明**：
- `web/` 目录仅存放纯静态资源（HTML/CSS/JS），无任何服务端代码；
- 路由逻辑统一放置在 `rps_core/api/routes.py`，确保前端可独立部署；
- 前端支持全静态运行，可通过 CDN、IPFS 或本地文件直接打开；
- FWUI 目录存放独立的 UI 组件库，管理弹窗、提示等所有交互组件。

### 3. 链上合约层（Polygon · 最终信任仲裁层）

**技术**：Solidity 0.8.20+ EVM 标准合约

**承担项目所有核心可信逻辑**：
- 对局创建、加入、资金锁定；
- 哈希承诺存储、揭晓校验、防作弊判定；
- 超时自动结算、弃权判负；
- 胜负计算、奖金分发；
- 手续费全自动链上抽水（费率可由 Owner 调整）；
- 硬编码原版防仿标识、运维钱包地址；
- 预留二期生态扩展字段（赛事、NFT、房间类型）。

**开源要求**：100% 开源、链上可验证、永久公开透明。

**合约核心数据结构**：
```solidity
struct Game {
    address player1;           // 玩家1地址
    address player2;           // 玩家2地址
    uint256 amount;            // 下注金额
    address token;             // 代币地址
    bytes32 commit1;           // 玩家1承诺
    bytes32 commit2;           // 玩家2承诺
    uint8 choice1;             // 玩家1选择(0=石头,1=剪刀,2=布)
    uint8 choice2;             // 玩家2选择
    uint256 commitDeadline;    // 提交截止时间
    uint256 revealDeadline;    // 揭晓截止时间
    GameStatus status;         // 状态(等待/提交中/揭晓中/结束)
    address winner;            // 胜者地址
    bool isDraw;               // 是否平局
}
```

## 五、网络交互模型（最终定稿）

非纯 C2C、非中心化，为 **「链下辅助通信 + 链上完全 C2C 资产结算」混合可信模型**

```
用户 ↔ 用户
  ↖   ↗
   链上合约（资金结算）
   ↕
  链下后端（仅匹配/通知）
```

- 用户与用户之间 **资金、博弈、结算完全点对点链上执行**；
- 中心化后端仅做「找人、发通知」，不做中间资金托管、不做结果判定；
- 用户可手动关闭所有中心化链路，实现纯链上 P2P 对局；
- 模式 B 下，前端与后端完全隔离，仅保留与 Polygon RPC 的链上交互。

## 六、合约接口与事件

### 合约核心接口

| 函数 | 可见性 | 功能 | 参数 |
|------|--------|------|------|
| `createMatch(uint256 amount, address token)` | external | 创建对局 | 下注金额、代币地址 |
| `joinMatch(uint256 gameId)` | external | 加入对局 | 对局ID |
| `submitCommit(uint256 gameId, bytes32 commit)` | external | 提交哈希承诺 | 对局ID、哈希密文 |
| `revealChoice(uint256 gameId, uint8 choice, bytes32 salt)` | external | 揭晓出拳 | 对局ID、选择、盐值 |
| `claimTimeout(uint256 gameId)` | external | 超时索赔 | 对局ID |
| `handleDraw(uint256 gameId)` | external | 平局处理 | 对局ID |
| `getGame(uint256 gameId)` | view | 查询对局状态 | 对局ID |
| `getCommit(uint256 gameId, address player)` | view | 查询承诺 | 对局ID、玩家地址 |

> 注：函数命名以实际合约为准，以上为逻辑接口说明。

### 合约事件监听

```text
// 监听对局创建
contract.on('GameCreated', (gameId, creator, amount, token) => { ... });

// 监听承诺提交
contract.on('CommitSubmitted', (gameId, player, commit) => { ... });

// 监听揭晓
contract.on('ChoiceRevealed', (gameId, player, choice) => { ... });

// 监听结算
contract.on('GameSettled', (gameId, winner, amount, fee) => { ... });

// 监听超时
contract.on('TimeoutClaimed', (gameId, claimer) => { ... });

// 监听平局
contract.on('DrawHandled', (gameId, ...) => { ... });

// 监听手续费率变更
contract.on('FeeRateChanged', (newRate, ...) => { ... });

// 监听合约取消
contract.on('MatchCancelled', (gameId, ...) => { ... });
```

## 八、防仿标识机制

### 什么是防仿标识

防仿标识是内嵌在智能合约中的一组不可篡改的身份信息，用于证明某份合约是 ChainRPS 官方原版，而非仿盘部署的。

### 防仿标识包含的内容

| 标识项 | 说明 | 是否可更改 |
|--------|------|------------|
| 官方开发者地址 | 部署时硬编码的官方钱包地址 | ❌ 不可更改 |
| 合约部署时间戳 | 合约部署到链上的区块时间 | ❌ 不可更改 |
| 合约版本号 | 标识合约版本（如 v1.0.0） | ❌ 不可更改 |
| 官方域名 / 社交链接 | 官方网站、Twitter、Discord 等 | ⚠️ 可由 Owner 更新 |

### 用户如何验证正版

**方式一：前端自动验证**
- 前端连接到合约后，自动读取合约中的防仿标识；
- 与内置的官方标识进行比对；
- 如不一致，在页面显著位置警告用户「可能为仿盘」。

**方式二：手动链上验证**
1. 在区块浏览器（如 Polygonscan）打开合约地址；
2. 查看合约源码中的硬编码开发者地址和部署时间；
3. 与官方公布的地址和时间进行比对；
4. 部署时间最早的为原版。

### 防仿标识的意义

| 壁垒 | 说明 |
|------|------|

## 九、历史记录数据策略

### 分层查询策略

| 层级 | 数据源 | 特点 | 使用场景 |
|------|--------|------|----------|
| 一级（优先） | 后端 SQLite 数据库 | 速度快、查询灵活、支持分页和筛选 | 默认查询、列表页、快速加载 |
| 二级（降级） | 链上事件日志 | 数据最权威、不可篡改 | 数据对账、后端不可用时、验证数据 |

### 数据同步机制

- 后端监听合约事件，实时同步到本地 SQLite 数据库；
- 后端启动时进行数据校验，确保本地数据与链上一致；
- 用户查询历史时优先走后端，如后端数据缺失或异常，降级为直接查询链上。

### 代币授权机制

| 项目 | 说明 |
|------|------|
| 授权方式 | 每局授权一次 |
| 授权额度 | 单笔下注金额（非无限授权） |
| 安全性 | 单笔授权降低风险，用户每笔交易都有明确感知 |
| 流程 | 1. 授权单笔额度 → 2. 创建/加入对局 |
